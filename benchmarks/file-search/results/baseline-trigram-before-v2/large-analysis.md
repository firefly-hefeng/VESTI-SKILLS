# 文件定位大规模实验结论

## 结论

`vesti_search_files` 已通过真实 APP MCP 链路完成 72 题配对实验，但当前结果不支持“全面提升”或“可以发布”的结论。

- 主成功率从旧流程的 **51.5%** 提升到 **57.6%**，绝对提升 **6.1 个百分点**。
- 以 12 个独立概念簇做 cluster bootstrap，95% CI 为 **-8.7% 到 +17.9%**，跨过 0。
- 新工具在“只知道文件名”的任务上从 **0% 提升到 91.7%**，这是明确的新能力。
- 语义单文件、多文件和陈旧路径检索分别回退 16.7、25.0 和 16.7 个百分点；跨项目成功率持平。
- 新工具把中位调用数从 7 次降到 1 次，把模型可见 payload 从 6,217 B 降到 1,978 B；这是本轮环境中的描述性结果，不等同于真实产品端到端延迟。

因此目前只能说：**新工具大幅降低了调用和上下文成本，并补齐文件名反查能力，但语义召回与排序仍有结构性缺陷。**

## 实验规模与链路

- 72 个 case，来自 12 个概念簇；每个 case 两个 arm，每个 arm 先预热 2 次，再计时运行 10 次。
- 8 个项目、146 个合成会话、292 条消息、192 条工具调用。
- 六个任务层各 12 题：语义单文件、文件名、多文件、跨项目、陈旧路径、负例。
- 测试库使用与当前 APP migration 一致的 FTS5 `trigram` tokenizer。
- 链路为：临时 SQLite/FTS → VESTI-APP 已构建 MCP 公共入口 → 官方 SDK `Client + InMemoryTransport` → 真实 MCP tools/call。
- 被测 APP MCP 完整 dist artifact SHA-256：`8532a1358d5dbdaefe3c5776d5d17c5498bd2afa3213197f17ce32e36272296f`。
- 10 次计时重复中没有运行错误，也没有同题结果漂移。

主质量指标统计 60 个正例和 6 个 clean negative。6 个 hard negative 仅从主质量指标排除，仍纳入检索压力和运行成本统计；它们衡量的是“是否返回任意候选”，不能直接等同于 Agent 最终幻觉。

## 失败原因

### 1. Trigram 对两字中文词的召回存在盲区

生产 schema 的 trigram tokenizer 不能独立匹配少于 3 个字符的 token。召回层会把连续短 token 合并为短语，但查询 `采集 增量 防护在哪个文件` 会生成类似 `"采集 增量"` 的短语，而历史文本是 `采集 流程针对 增量`，并不包含这个连续短语，因此返回空结果。capture、membership 等中文任务暴露了这一问题。

这不是 fixture 偏差：本轮 fixture 已与当前 APP 的 trigram schema 对齐。后续应改查询规划或补充 n-gram/LIKE/向量召回，而不是退回旧 tokenizer。

### 2. “任意路径 token 命中 +3”权重过大

当前只要路径包含查询中的任意 token，就增加 3 分，而会话内容召回贡献通常只有约 0.55 分。结果中可以直接观察到：

- `src/noise/dashboard/note*.md` 得分约 3.55，长期压过语义目标。
- migration 多文件题有两个 3.5 分干扰项，四个正确文件排在第 3–6 名，最后一个目标跌出 Top 5。
- proxy、embedding、export、localization 的通用 `*Panel.tsx` 路径也会抢占前排。

文件名证据方向是正确的，但当前是“任一子串布尔命中”，没有区分完整 basename、token 覆盖率、词的稀有度和普通主题词；同分时又由 touches 和稳定插入顺序决定名次。

### 3. 短停用词和项目限定没有结构化处理

`languageRegistry.ts in skills` 的目标排到第 10。查询 token 包括 `languageRegistry.ts`、`in`、`skills`；两字符停用词 `in` 会通过 substring LIKE 命中 `embedding`、`Indigo` 等无关路径。与此同时，`skills` 只是普通 token，并不会把候选限定到 `C:/bench/vesti-skills`。

因此需要同时处理 stopword/最短 token、完整文件名匹配和显式项目过滤，不能只简单提高文件名权重。

### 4. 多目标结果缺少与任务类型匹配的覆盖策略

跨项目任务可以受益于 project diversity，避免同一项目的其他文件挤掉第二个项目目标。但同项目多文件可能全部来自同一会话，不能直接采用“每个 session 只留一个文件”的配额，否则反而会损害正确召回。需要根据查询意图区分单文件、同项目多文件和跨项目覆盖策略。

### 5. 会话候选上限仍需单独消融

语料包含超过 `SESSION_RECALL_LIMIT = 12` 的高 fan-out 压力簇，最终结果也出现目标缺失。不过当前结果文件没有保存内部 recall Top 12，且部分失败同时受到 trigram 和路径加分影响，所以不能仅凭本轮结果断言“全部由截断导致”。下一轮应记录内部候选并分别跑 limit=12/30 的消融实验。

## 实验决策

当前不进入大规模 Agent 2×2 归因实验。检索层尚未达到预设门槛：单文件 Hit@3 未达到 90%，多文件/跨项目 Recall@5 未达到 85%，并且存在明确排序回归。此时继续花费模型 Token，只会把已知底层缺陷带入 Agent 结果。

下一轮应先在独立分支修改检索算法，并保持这 72 题、语料、APP MCP 入口和评分脚本不变进行回归复测。建议按以下顺序处理：

1. 修复 trigram 下两字中文词的查询规划与召回兜底。
2. 文件名加分改为完整 basename、token 覆盖率和稀有度加权，并过滤 `in` 等短停用词。
3. 支持显式项目路径或项目名过滤，不把项目提示混入普通 token。
4. 记录内部 session recall trace，消融比较候选上限 12 与 30。
5. 对跨项目结果增加 project-aware coverage；同项目多文件采用 group-aware coverage，避免硬性 session 配额。
6. 检索门槛通过后，再做“旧/新工具 × 无/有 Skill”的 Agent 四臂盲测，独立量化工具和 Skill 指令贡献。

本轮 `provisional-holdout` 已被查看，只能视作普通测试集。正式发布结论前必须用独立 concept bank 生成真正隐藏的 holdout。
